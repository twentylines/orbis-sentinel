# Sentinel package activation

`activate_release.py` is the Linux root installer for the managed Sentinel status service. It verifies the archive's publisher, source commit and complete payload before changing the service. Supply a reviewed checksum, component version, full source commit, downloaded Sigstore bundle, a fresh private verification workspace and an independently trusted GitHub CLI executable, using `--artifact`, `--bundle`, `--workspace`, `--sha256`, `--version`, `--source-commit` and `--verifier`. The installer and its Python companions must come from a trusted source; a package being downloaded cannot authenticate its own installer.

The managed installation lives at `/opt/orbis-sentinel`, with immutable payloads under `releases` and a relative `current` selector. Root-owned transaction records and the installed-payload receipt live in `/var/lib/orbis-sentinel`, mode `0700`. The installer holds an exclusive activation lock and records admission before changing files. It installs only the recognized `orbis-sentinel.service` and `orbis-sentinel.socket` profile, then checks systemd's active service invocation and the root-owned health socket against the candidate version. A successful command returns `activated: true` only after those checks and the installation receipt complete.

An update preserves every existing version directory. Capture profiles can pin an older canonical bundle path, so an inactive version is not automatically disposable. A failed startup restores the previous verified selector, unit enablement and activity when the supervisor confirms quiescence and the recorded identities still agree. First-install rollback removes only unit files created by that transaction. It retains the candidate, admission record and journal. A fresh retry authenticates the package again and may reuse its existing version directory only after checking the entire tree against the authenticated archive; it never replaces that directory.

An interrupted transaction, changed selector, changed managed files, uncertain supervisor state or unsuccessful rollback leaves a reconciliation hold. Re-running the command does not replay the interrupted transaction. Retain the journal and runtime directories for an independent root review rather than deleting them to force another attempt.

Existing manual installations without a managed receipt, customized unit files and systemd drop-ins require a separate adoption or profile review. The installer preserves them. A changed signed systemd profile also requires a compatible reviewed installer update; an independently updated Sentinel payload does not silently broaden the service's privileges.

This installer operates the status-service unit. It does not change Orbis enrollment, create another controller socket mount, authorize recovery jobs or transfer ownership from an external worker. Orbis installer/OTA wiring, independent recovery authentication and installed systemd acceptance are separate integration requirements.
