# Sentinel package activation

`activate_release.py` is the Linux root installer for the managed Sentinel status service. It verifies the archive's publisher, source commit and complete payload before changing the service. Supply a reviewed checksum, component version, full source commit, downloaded Sigstore bundle, a fresh private verification workspace and an independently trusted GitHub CLI executable, using `--artifact`, `--bundle`, `--workspace`, `--sha256`, `--version`, `--source-commit` and `--verifier`. The installer and its Python companions must come from a trusted source; a package being downloaded cannot authenticate its own installer.

The managed installation lives at `/opt/orbis-sentinel`, with immutable payloads under `releases` and a relative `current` selector. Root-owned transaction records and the installed-payload receipt live in `/var/lib/orbis-sentinel`, mode `0700`. The installer holds an exclusive activation lock and records admission before changing files. It installs only the recognized `orbis-sentinel.service` and `orbis-sentinel.socket` profile, then checks systemd's active service invocation and the root-owned health socket against the candidate version. A successful command returns `activated: true` only after those checks and the installation receipt complete.

An update preserves every existing version directory. Capture profiles can pin an older canonical bundle path, so an inactive version is not automatically disposable. A failed startup restores the previous verified selector, unit enablement and activity when the supervisor confirms quiescence and the recorded identities still agree. First-install rollback removes only unit files created by that transaction. It retains the candidate, admission record and journal. A fresh retry authenticates the package again and may reuse its existing version directory only after checking the entire tree against the authenticated archive; it never replaces that directory.

An interrupted transaction, changed selector, changed managed files, uncertain supervisor state or unsuccessful rollback leaves a reconciliation hold. Re-running the command does not replay the interrupted transaction. Retain the journal and runtime directories for an independent root review rather than deleting them to force another attempt.

A coordinated Root caller may pass `retain` to `activate_release` with its canonical UUID4 `operationId`, `planSha256` and exact Core `targetDigest`. This optional API requires an existing healthy managed collector. It records a private immutable retention admission before activation and returns a `retainedRollback` ticket only after the new version is healthy. Ordinary CLI activation and first installation do not create these tickets.

`restore_retained(ticket)` restores only the exact previous runtime from that most recent completed activation. It has no target-version, path or force option. The activation, original admission, ticket, both immutable runtime inventories, installed selector, service units and original observer profile must still agree. A separate integration stage must restore any changed observer profile first. The restoration records a new admission and durable intent, stops the managed collector, restores its recorded selector and unit state, and checks the exact old version's health before publishing a new completed installation receipt. Both original admissions and runtime directories remain intact. Repeating a completed restoration observes the same healthy installation without restarting it; a later activation spends that ticket. Any uncertain restoration remains held for independent reconciliation, including loss of the final receipt after selecting the old runtime. This API does not authorize or implement the Core/Host coordinator.

Existing manual installations without a managed receipt, customized unit files and unrecognized systemd drop-ins require a separate adoption or profile review. The installer preserves them. An existing `orbis-observer-v1` or `orbis-observer-v2` configuration can be retained across a collector update only when its private Root-owned `observer-profile.json` receipt, exact selected collector and Host observer templates, local group identity and loaded systemd paths all agree. Activation does not enroll a profile or create its receipt. A changed or unrecorded profile remains blocked; a change during activation leaves reconciliation required. A changed signed systemd profile also requires a compatible reviewed installer update; an independently updated Sentinel payload does not silently broaden the service's privileges.

The optional v2 collector template is packaged at `packaging/systemd/observer-profiles/upgrade-observer.conf`; the installed drop-in remains `orbis-sentinel.service.d/observer.conf`. It adds a separate read-only progress observer at `/run/orbis-upgrade/progress.sock`. That peer has the same bounded GET protocol and Root socket/peer checks as the Host observer. Its worker reads only update progress; component, capture and handoff observations still come from Host. A fresh independent update can remain visible while Host is unavailable. Stale or unavailable independent observations cannot retain success, and conflicting active operation identities are not combined. The default collector has no additional observer or worker. This profile does not implement the independent updater, grant it authority, or certify an installed coordinated upgrade.

This installer operates the status-service unit. It does not change Orbis enrollment, create another controller socket mount, authorize recovery jobs or transfer ownership from an external worker. Orbis installer/OTA wiring, independent recovery authentication and installed systemd acceptance are separate integration requirements.
